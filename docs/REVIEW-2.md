### Attacked and held (no finding)

- **Lock order, all RPCs.** I traced every multi-lock function against ARCH §5.1:
  - `start_attempt`, including the stale-reap branch at step 4, which locks `ai_spend` before the new attempt row. That is safe, because the new row is not visible to any other transaction and the user is serialized by the wallet lock.
  - `record_attempt`, `repair_glass`, `donate`, `admin_grant_funds`, `reap_stale_attempts`, `touch_presence`, `admin_set_player_hidden`, the rule RPCs, `claim_hardening_job`, and `claim_lease`.

  No cycle exists. The `game_state` singleton is locked before any `ai_spend` row by every function that touches both, so it also serializes the reaper against a stale reap inside `start_attempt`. The R1-02 inversion is gone.
- **One paid win per epoch and `late_win`.** Under READ COMMITTED, the second winner re-reads the locked `game_state` row and sees epoch e+1, so it becomes `late_win` (ARCH L838-839). The unique index `attempts_one_win_per_epoch` (L587) is a backstop.
- **Atomic $1 debit before any model call.** The debit happens at `start_attempt` step 5. A spend-cap refusal at step 9 rolls the fee back.
- **Insufficient funds** is refused with PT402 and charges nothing.
- **Repair at 0 cracks** is refused with no charge. Repair replay is keyed by the ledger `external_ref`.
- **Donation bounds** run from 1 cent to the stored balance. Donation replay uses the unique `(user_id, idempotency_key)`.
- **Aura edge cases.**
  - 0/0 gives 0.
  - A balance of 0 with donations above 0 gives 10000.
  - It uses integer floor division in a generated stored column (ARCH L541-544).
  - The glow extent is spread plus blur, at most 10 px.
- **crack_count isolation.** It is absent from `start_attempt`'s result (L773), from the `runAttempt` type, from the engine envelope (§6.9), and from the Decisions request. PP-26 `hc3-isolation.test.ts` asserts identical model, validator, evaluator, and engine inputs at 0 and 3 cracks.
- **The CH-6b blocklist source** is enforced in four places: the `trigger = 'win'` CHECK, `insert_rule_proposal`, `add_breach_to_golden`, and the `p_block_fingerprint requires win` invariant. A pgTAP test covers every non-win outcome. `late_win` is excluded (A11).
- **HC-A1 paths.** No route carries `block_keywords`, traffic prompts, or breach rows into any prompt. The engine gets booleans and enum signals only (§6.9).
- **HC2 and HC-A2.** The fixed developer prompt contains the exact HC2 phrases. The JSON-encoded payload sits in 128-bit nonce tags in the user role, with strict `json_schema` output.
- **HC4.** Stage A is deterministic and two-way, and the rule set reaches only the validator. A `proposed` row is inert, so "committed" is read as "activated". That reading is acceptable.
- **The R1-01 question: can a winner still DoS a level?** Not in practice.
  - Each paid win can add at most 3 phrases. Each must be evidence-bound, carry a content token, be rare in traffic, and pass the benign and loophole pre-filters.
  - Lineages at levels 1 to 4 stay dormant until a game reset, because the shared pig moves on after a win.
  - Only level 5's lineage is live while it is being hardened, and there every attack is hostile by definition.
  - Residual gaps are in R2-15.
- **Realtime publication** is pinned to `game_state` and `live_feed`, with no free-text columns. A pgTAP test and a static allowlist script guard it.
- **Coming-soon rails** install no SDK, perform no I/O, have the factory throw for any non-mock mode, and the components do not import the payments module.
- **RLS policies follow the Supabase skill:** `TO <role>` plus an ownership predicate, `(select auth.uid())`, no views, and no `user_metadata` used in authorization decisions. R2-06 covers its use for display.
- **Task graph mechanics, checked by script.**
  - Every `depends_on` points to an earlier group.
  - Every `files_owned` overlap (`database.ts`, migrations README, `ci.yml`, `layout.tsx`/`page.tsx`/`globals.css`, `levels.ts`, `level-policies.ts`, `pricing.ts`, validator fixtures, `src/lib/rules/**`) is ordered by transitive `depends_on`.
  - Every output is covered by `files_owned`.

### Claims verified during this review

- **Supabase Realtime Free limits:** 200 concurrent connections, 100 messages per second, 100 channel joins per second, 10 presence keys per object, and 20 presence messages per second. These match ARCH §12.4 (supabase.com/docs/guides/realtime/limits). The docs also say "Private and public channels can subscribe to Postgres Changes" (supabase.com/docs/guides/realtime/authorization).
- **OpenAI Responses API.** Reaching `max_output_tokens` returns `status: "incomplete"` with `incomplete_details.reason` set to `max_output_tokens` or `content_filter`. Reasoning tokens count toward the cap, and an incomplete response can come back before any visible output (developers.openai.com/api/docs/guides/reasoning).
- **Vercel environment variables.** `VERCEL_URL` is "the domain name of the generated deployment URL" and "cannot be used in conjunction with Standard Deployment Protection". `VERCEL_BRANCH_URL` is the `*-git-*` branch alias. Vercel Authentication and Standard Protection, which protect preview URLs, are available on all plans and are the recommended setting (vercel.com/docs/environment-variables/system-environment-variables and vercel.com/docs/deployment-protection).
- **Supabase skill.** Three points matter here:
  - "`raw_user_meta_data` is user-editable".
  - "Anonymous users carry the `authenticated` Postgres role".
  - Keep `SECURITY DEFINER` and internal functions in a non-exposed schema, and run `supabase db advisors` before committing a migration.
